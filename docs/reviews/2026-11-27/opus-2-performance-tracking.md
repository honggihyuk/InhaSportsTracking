## 1) 잘한 점

1. **묶음 처리로 바뀐 것은 실행 방식뿐이고 판정 규칙은 그대로다.**
   - `track_many`(`tracking/sam_video.py:251-296`)는 덩어리마다 영상을 한 번 읽는다.
   - 프레임 영상 특징은 `_FrameFeatureCache`(`:166-202`)에 한 번 계산해 둔다.
   - 사건이 바뀔 때마다 `reset_tracking_data()`로 추적 상태(메모리)만 비운다.
   - ID 교체로 뒤 사건의 프롬프트 박스가 달라지면 `_same_prompts`(`:159`, `:466`)로 알아채고 그 사건만 다시 전파한다(`recomputed`).

   "앞 사건의 결과가 뒤 사건의 입력을 바꾼다"는 순차 의존성을 놓치지 않았다. 묶음 최적화에서 가장 흔히 깨지는 부분이 이것이다.

2. **"결과가 같다"는 주장을 세 단계로 검증했다.**
   - 단위 테스트: 끊김 2곳, 교체 1곳, 교체 뒤 프롬프트가 바뀌는 겹침 1곳이 있는 장면을 만들었다(`tests/test_sam_video_batch.py:113-158`).
   - 실제 SAM3 스모크: 박스 227/227이 일치했다(12부).
   - 전체 영상 두 번 실행: 프레임 박스, 경기장 좌표, 호모그래피가 모두 일치했다(`tracking-comparison.json`).

   성능 최적화를 넣을 때 정확도가 같다는 것까지 증명한 점이 훌륭하다.

3. **GPU 없이 핵심 로직을 테스트할 수 있게 짰다.**
   - `repair_tracks`는 `hasattr(tracker, 'track_many')`로 기능을 확인한다(`:390`). 그래서 가짜 추적기를 그대로 꽂을 수 있다.
   - 테스트는 "진짜 선수 위치를 아는 가짜 SAM"(`OneByOneTracker`)과 `read_frames` monkeypatch로 판정 로직을 검증한다.
   - 위치 임베딩 공유 캐시도 CPU 텐서로 따로 테스트했다.

4. **판정 근거를 결과에 남긴다.**
   - `repair_tracks`는 `link_iou`, `swap_evidence`(crossed/compared/mean_diff), `batches`, `recomputed`, `seconds`를 요약에 넣는다(`:498-502`).
   - `identify`는 재연결 전 투표(`votes`)와 원문 판독(`texts`)을 보존한다(`tracking/identity.py:287`, `:305`).

   나중에 "왜 이 두 트랙이 합쳐졌지?"를 추적할 수 있다. 실무에서도 아주 중요한 습관이다.

5. **ID 교체 판정을 보수적으로 설계했다.** 떨어진 뒤 `swap_frames` 이상, 그리고 비교한 프레임의 `swap_ratio`(80%) 이상에서 엇갈려야 교체한다(`:483-484`). 마스크가 잠깐 흔들리는 것을 걸러낸다. "진짜로 교차한 선수는 바꾸지 않는다" 테스트(`tests/test_sam_video.py:108`)도 있어서 거짓 양성을 막는 의도가 코드와 테스트 양쪽에 드러난다.

6. **등번호 규칙의 근거가 데이터다.**
   - '1' 판독을 골키퍼에게만 인정하는 규칙(`identity.py:276`)은 실제 오독 사례(심판 2명이 1번으로 확정)에서 나왔다.
   - `min_frac`은 "크롭 대부분이 안 읽혔는데 우연히 두 번 맞은 경우"를 거른다.
   - 사람이 크롭 시트로 정밀도 8/8을 확인했다.

7. **`eval_suite.py`를 재현 가능한 실험 도구로 만들었다.**
   - `--variant` 키를 `PERF_DEFAULTS`로 검증한다(`:84-99`).
   - 설정마다 기준값으로 되돌린 뒤 덮어쓴다(`apply_variant`, 테스트 있음).
   - 분석 순서를 `backend/server.py`와 맞췄다.
   - JSON과 Markdown을 함께 저장한다.

8. **보고서 서술이 정직하다.** 3절은 "이번 한 쌍에서"라고 범위를 한정했다. VRAM +33.9%라는 비용도 숨기지 않았고, 6절에서 "동일 조건의 반복 실행으로 변동 폭을 측정해야 한다"고 스스로 한계를 적었다.

### 2-1. [pipeline/video_analysis.py:356-383, tracking/sam_video.py:441·486] `frames`와 부가 테이블(crops·colors·labels·bank)의 ID 계약이 깨질 수 있다
**심각도: 중요**

**왜 문제인가**

`frames`의 트랙 ID는 세 번 바뀐다: `stitch_tracks`, `repair_tracks`, `identify`. 그때마다 `track_crops`, `track_colors`, `track_labels`, `jersey_bank`가 같은 ID 체계를 따라와야 한다. 지금은 세 장면에서 어긋난다.

1. **순서 문제.** `stitch_tracks`(356행)는 `frames`와 `track_colors`만 즉시 바꾼다. `track_crops`와 `track_labels`의 stitch 병합(379-383행)은 SAM 병합(365-370행)보다 *뒤에* 실행된다.
   - 예: stitch가 `c1 → r1`로 이은 뒤 SAM이 `r1 → a`로 잇는다.
   - SAM 병합이 `r1`의 crops와 labels를 `a`로 옮긴다.
   - 그다음 stitch 병합이 `c1`의 crops와 labels를 `r1`에 넣는다. 그런데 `r1`은 이미 `frames`에 없다.
   - 결과: `a`는 `c1`의 라벨 표가 빠져 심판·골키퍼 다수결이 뒤집힐 수 있다. `r1`은 팀 분류에 "유령 트랙"으로 들어가 `teams`와 `track_labels` 출력에 남는다.

   stitch는 같은 선수의 끊긴 조각을 색으로 잇고, SAM은 stitch가 놓친 곳을 잇는다. 둘 다 같은 트랙에 작용하는 경우는 드물지 않다.

2. **부분 실패.** `repair_tracks`는 `frames`를 제자리에서 고친다. 1단계 끝의 `apply_links`(441행) 다음, 2단계에서 예외가 나면(예: 2단계 `_precompute`의 CUDA OOM) 상태가 어긋난다.
   - except 블록(375-377행)은 "기존 추적 결과 유지"라고 출력한다. 하지만 `frames`는 이미 이어진 상태다.
   - crops, colors, labels, bank는 이어지기 전 상태로 남는다.
   - 결과: 자식 트랙의 등번호 크롭은 `identify`에서 버려진다(`ids = {… if tid in spans}`). `track_colors`의 자식 키는 `teams`에 유령으로 남는다.

3. **교체는 bank에만 반영된다.** `jersey_bank.swap(swaps)`(373행)는 프레임 번호로 크롭 주인을 바꾼다. 하지만 `track_crops`(팀 분류용), `track_colors`, `track_labels`는 그대로다. 겹침 뒤 교체는 상대 팀 선수끼리 자주 일어난다(태클 장면). 그러면 한 트랙의 팀 표본에 상대 팀 유니폼이 섞인다. `track_crops`는 프레임 번호를 저장하지 않으므로 지금 구조로는 교체를 반영할 수도 없다.

**일관성(규칙 3):** "ID 다시 매기기"가 세 곳에 따로 구현되어 있다.
- `sam_video.apply_links`(337행)
- `identity.apply_relink`(237행)
- `stitch_tracks` 안의 인라인 루프(postprocess 156-159행)

부가 테이블 병합도 365-370행과 379-383행에 미묘하게 다른 형태로 반복된다(한쪽만 colors 포함). 1번 버그는 이 중복에서 나왔다.

**생각해볼 질문**
- `frames`와 부가 테이블 가운데 "진실의 원천"은 어느 쪽이어야 할까? 부가 테이블은 `frames`에서 언제든 다시 유도할 수 있어야 할까?
- `repair_tracks`가 실패하면 호출자는 "아무것도 안 바뀌었다"를 믿을 수 있어야 할까, "바뀐 만큼은 반영한다"를 믿을 수 있어야 할까?

**선택 가능한 접근**

| 접근 | 장점 | 단점 |
|---|---|---|
| A. 각 ID 변경 단계 직후 부가 테이블을 바로 병합 (stitch 직후 crops·labels 병합) | 변경이 가장 작다 | 다음에 단계를 추가할 때 또 순서를 맞춰야 한다 |
| B. ID 변경을 `{child: root}`와 `(a, b, 시작 프레임)` 이벤트 로그로 모으고, `remap_side_tables` 같은 한 함수로 일괄 적용 | 규칙이 한 곳에 모인다. 테스트하기 쉽다 | crops에 프레임 번호를 같이 저장해야 swap까지 반영된다 |
| C. `repair_tracks`를 복사본 위에서 돌리고 성공했을 때만 교체(트랜잭션) | 실패 시 "원래대로"가 보장된다 | `frames` 복사 비용이 든다. 1분 영상 기준 수십 MB 수준이라 감당할 만한지는 측정해 봐야 한다 |

**관련 학습 개념:** 파생 상태 동기화(single source of truth)와 실패 원자성(all-or-nothing). 데이터베이스의 트랜잭션 개념을 파이프라인 단계에 적용하는 연습이다.

### 2-2. [tracking/sam_video.py:121-139, 166-202, 350-367] `max_span`은 GPU 메모리 상한이 아니고, OOM 때 대체 경로가 없다
**심각도: 권장**

**왜 문제인가**

설정 주석과 12부는 "프레임당 약 9 MB, `max_span` 120이면 최대 약 1.1 GB"라고 설명한다. 그런데 `merge_windows`는 *`max_span`보다 긴 구간 하나는 혼자 한 덩어리*로 둔다(127행 docstring, 테스트도 이 동작을 확인한다).

- 겹침 사건의 길이는 `lead(8) + 겹친 길이 + window//2(15)`다. 그런데 `overlap_events`는 5프레임 이하 틈을 계속 이어 붙이므로 겹친 길이에 상한이 없다.
- 예: 두 선수가 10초 동안 나란히 뛰거나, 코너킥 때 몸싸움이 길게 이어진다. 그러면 300프레임 넘는 덩어리가 생기고, `_FrameFeatureCache`는 그 모든 프레임 특징을 GPU에 들고 있는다. 9 MB × 300이면 약 2.7 GB다.
- 사건별 처리(transformers 기본 캐시, 1프레임 보관)에서는 없던 메모리 증가다.
- 전체 실행에서 이미 5.02 → 6.72 GiB로 늘었다. 12 GB 카드에서 더 긴 영상이나 붐비는 장면을 만나면 OOM이 날 수 있다.

OOM이 나면 `repair_tracks` 전체가 예외로 끝난다.
- 1단계 `_precompute`에서 나면 SAM 보정 전체를 잃는다.
- 2단계에서 나면 2-1의 부분 실패 상태가 된다.

**생각해볼 질문**
- 메모리 상한을 "프레임 수"로 정하는 것과 "실제 바이트(해상도·특징 크기 반영)"로 정하는 것 중 무엇이 영상이 바뀌어도 안전할까?
- 긴 사건 하나가 상한을 넘으면 그 사건만 사건별 방식으로 처리하면 될까? 이미 `batch=False` 경로가 있다는 점을 활용할 수 있을까?

**선택 가능한 접근**

| 접근 | 장점 | 단점 |
|---|---|---|
| A. `max_span`보다 긴 사건은 묶지 않고 사건별 `track`으로 보낸다 | 단순하고, 메모리 상한이 실제로 지켜진다 | 긴 사건은 최적화 이득이 없다 |
| B. 덩어리 처리에서 `torch.cuda.OutOfMemoryError`를 잡아 캐시를 비우고 그 덩어리만 사건별로 재시도 | 평소 속도를 유지하고 실패할 때만 느려진다 | 예외 경로 테스트가 필요하다. OOM 뒤 메모리 단편화를 고려해야 한다 |
| C. 캐시를 LRU(최근 N프레임)로 제한 | 메모리가 고정된다 | 사건 순서에 따라 재계산이 생겨 이득이 줄어든다. 결과 동일성은 유지된다 |

**관련 학습 개념:** 배치 처리와 GPU 메모리의 공간-시간 트레이드오프. 그리고 "설정값이 보장하는 것과 보장하지 않는 것"을 문서에 정확히 적는 습관이다.

참고로 정밀 모드에서는 `SamRefiner`(SAM3 이미지 모델)가 분석이 끝날 때까지 VRAM에 남아 있다(`backend/server.py`의 finally에서 내림). 그래서 SAM 보정 구간에는 같은 `facebook/sam3` 가중치가 두 벌 올라와 있다. 피크 VRAM을 줄일 여지가 있는지 한 번 측정해 보면 좋겠다.

### 2-3. [tracking/sam_video.py:471, 223-227, 307-320] 영상 다시 읽기가 실패하면 `IndexError`가 난다. seek 정확도도 결과 동일성의 숨은 전제다
**심각도: 권장**

**왜 문제인가**

- 1단계는 `len(clip) < 2`를 확인한다(417행). 그런데 2단계의 사건별 경로와 묶음의 재전파 경로는 `tracker.track(read_frames(...), prompts)`를 바로 호출한다(471행).
- `read_frames`가 빈 리스트를 돌려주면 `track`의 `frames_rgb[0]`(227행)에서 `IndexError`가 난다. 그 시점은 링크가 이미 적용된 뒤이므로 2-1의 부분 실패로 이어진다.
- 빈 리스트가 나오는 경우: 손상 파일, 가변 프레임레이트(VFR), 일부 코덱에서 `CAP_PROP_POS_FRAMES` seek 실패.

그리고 사건별 경로와 묶음 경로는 같은 프레임을 다른 방식으로 읽는다.
- 사건별: `e`로 seek한다.
- 묶음: 덩어리 시작 `gs`로 seek한 뒤 잘라 쓴다.

"결과가 같다"는 보장은 두 방식이 같은 프레임을 돌려준다는 전제 위에 있다. `analyze_video`는 처음부터 순차로 읽었으므로 seek 결과가 분석 때의 프레임 번호와 맞는지도 같은 전제다. sports_video_1(mp4)에서는 일치가 확인됐다. 다른 형식에서는 아직 모른다.

**생각해볼 질문**
- 1단계와 2단계의 "프레임 부족이면 건너뛴다" 규칙을 한 곳으로 모을 수 있을까? 이미 `track_jobs`(145행)에 같은 규칙이 있다.
- 분석 때 읽은 프레임과 재읽기한 프레임이 같은지 싸게 확인하는 방법은? 예: 분석 때 몇 프레임의 축소 해시를 남겨 두는 방법.

**선택 가능한 접근**
- A. 2단계에도 1단계와 같은 가드를 둔다. 가장 작은 변경이다.
- B. `read_frames`가 요청한 길이를 못 채우면 경고를 남기고, 요약에 `short_reads` 같은 집계를 추가한다. 관측 가능성이 좋아진다.

### 2-13. [pipeline/main_pipeline.py:173-179] 영상 추적기에는 SAM2.1 대체 경로가 없다
**심각도: 사소, 일관성**

`make_sam_refiner`는 `sam_fallback`(SAM2.1)으로 대체할 수 있다. `make_video_tracker`는 SAM3만 시도한다. Hugging Face 승인이 없는 환경에서는 refiner는 SAM2.1로 돌고 SAM 보정은 조용히 `{'error': …}`로 빠진다. 같은 설정 블록에서 동작이 다르다. 의도라면 설정 주석에 "sam_video는 대체 없음"을 적어 두고, 아니라면 `Sam2VideoModel`로 대체할 수 있는지 검토해 볼 만하다.

**관련 학습 개념:** 대체 정책(graceful degradation)을 컴포넌트 사이에 일관되게 적용하기.
