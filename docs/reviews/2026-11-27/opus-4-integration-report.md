### 2-1. [중요] 기본 샘플이 보고서에서 설명한 결과와 다릅니다 — 채점자가 첫 화면에서 보는 것은 수정 전 데이터입니다
**[`data/samples/analysis/sports_video_1.mp4.json` · `README.md:132` · `backend/server.py:101-120,695-698`]**

**왜 문제인가**
README는 "처음 실행하면 분석 완료 샘플이 첫 화면에서 바로 열린다"고 안내합니다. 그런데 저장소에 들어 있는 샘플은 2026-10-15 커밋(`b25f79a`)에서 만든 것이고, 이번 과제 A·B·C를 적용하기 전 결과입니다. 직접 열어서 확인한 값은 이렇습니다.

| 항목 | 기본 샘플 (화면에 보이는 값) | 보고서가 말하는 제출본 결과 |
|---|---|---|
| 최고 속력 | **12.5 m/s** | 9.35 m/s (A 적용 후) |
| 10 m/s 넘는 선수 | **12명** | 0명 |
| 등번호가 있는 선수 | **0명** (`identities` 없음) | 등번호 확정 트랙 18 |
| SAM3 영상 추적 정보 | 없음 | 끊김 이음 2 / ID 교체 3 |

그래서 채점자가 README대로 실행하면 보고서 2절이 "고쳤다"고 한 12 m/s대 질주가 그대로 보입니다. 경기 질의에서 "등번호 10번은 얼마나 뛰었어?"라고 물으면 `player_stats(jersey_number=…)`가 항상 "인식된 선수가 없습니다"를 돌려줍니다. 게다가 `seed_samples`는 "이미 있는 파일은 건드리지 않음"이라서, 예전에 서버를 한 번 띄운 PC에서는 샘플을 새로 만들어도 반영되지 않습니다.

**생각해볼 질문**
- 기본 샘플은 "언제의 코드로 만든 결과인지"를 어디에 기록해야 할까요? 지금 결과 JSON에는 `version: 2`만 있고, 커밋이나 프로필 정보가 없습니다.
- 샘플 형식(스키마)이 바뀌면, 이미 `uploads/`에 복사된 옛 샘플은 어떻게 처리되어야 할까요?

**선택 가능한 접근**
1. **샘플을 제출본 코드로 다시 만들기** — 가장 직접적인 방법입니다. 대신 파인튜닝 가중치와 GPU가 필요하고, JSON·npz 크기(지금 약 3 MB)가 늘어날 수 있습니다.
2. **기존 샘플에 후처리만 다시 적용하기** — A(속력 필터)는 `diagnose_speed.py compare`처럼 저장된 결과에서 다시 계산할 수 있습니다. 비용은 낮지만 등번호·SAM3 결과는 생기지 않으므로, README에 "샘플에는 등번호·SAM3 추적이 없음"을 적어야 합니다.
3. **샘플 메타데이터 + seed 정책 바꾸기** — 결과에 생성 커밋이나 버전을 넣고, `seed_samples`가 "uploads 쪽이 더 오래된 버전이면 교체"하게 합니다. 사용자가 직접 다시 보정한 결과를 덮어쓰지 않으려면 사용자 수정 여부를 따로 구분해야 해서 조금 복잡해집니다.

**관련 학습 개념**: *데이터 출처(provenance)와 픽스처 버전 관리* — 데모 데이터도 코드처럼 "어느 버전에서 나온 것인지"를 기록해야 합니다.

### 2-3. [중요] OpenAI 호환 어댑터에서 tool call ID가 짝이 맞지 않습니다 — 유료 API로 바꾸면 두 번째 요청부터 실패합니다
**[`agent/llm.py:127-131` · `agent/runner.py:222`]**

**왜 문제인가**
OpenAI Chat Completions 규약에서 `role: tool` 메시지의 `tool_call_id`는 바로 앞 assistant 메시지의 `tool_calls[].id` 중 하나와 같아야 합니다. 지금 구조에서는:
- assistant 메시지(인덱스 *i*)의 ID는 `call_{i}_{k}`로 만들어집니다.
- runner가 넣는 tool 메시지(`runner.py:222`)에는 `tool_call_id`가 없어서, 어댑터가 `call_{j}`(*j*는 tool 메시지 자신의 인덱스)를 채웁니다.

*i*와 *j*는 항상 다르기 때문에 **ID가 절대 일치하지 않습니다.** 예를 들어 "가장 많이 뛴 선수는?" → `player_stats` 호출 → 결과를 붙여 두 번째 요청을 보내는 순간, ID 검증을 하는 서버(OpenAI API 등)는 400을 돌려주고, `ask_match`는 "질의 실패" 500이 됩니다. vLLM·Ollama의 Qwen 템플릿은 ID를 무시하는 경우가 많아서 로컬에서는 문제가 드러나지 않았을 수 있습니다. `llm.py` 모듈 docstring과 `config:92-95`가 "유료 API로도 바꿀 수 있다"고 안내하는 만큼, 그 경로가 실제로 동작해야 합니다.

비슷한 문제가 하나 더 있습니다. `llm.py:146`에서 서버가 돌려준 `arguments` 문자열이 JSON이 아니면 `json.loads` 예외가 그대로 올라가 질문 전체가 500이 됩니다. 반면 Qwen 경로(`parse_tool_calls`)는 같은 상황을 조용히 건너뜁니다. 두 어댑터의 실패 처리 방식이 다릅니다.

**생각해볼 질문**
- tool call ID는 누가 "소유"해야 할까요? 모델(서버)이 준 ID를 끝까지 들고 다녀야 할까요, 아니면 어댑터가 일관된 규칙으로 새로 만들어야 할까요?
- `chat()`의 반환 계약(`{'content', 'tool_calls': [{'name', 'arguments'}]}`)에 `id`가 없다는 점이 원인일 수 있습니다. 이 계약을 넓히면 `QwenVLChat`은 어떻게 맞춰야 할까요?
- 이 버그를 실제 서버 없이 테스트로 잡으려면 무엇을 흉내 내야(mock) 할까요?

**선택 가능한 접근**
1. **공통 계약에 `id`를 추가하기** — 서버가 준 ID를 그대로 보존하고, Qwen처럼 ID가 없는 경우에는 어댑터가 만들어 줍니다. runner는 tool 결과에 그 ID를 실어 보냅니다. 가장 정석적이지만 두 어댑터와 runner를 모두 고쳐야 합니다.
2. **어댑터 안에서만 짝을 맞추기** — `_to_openai`가 메시지를 순회하면서 "직전 assistant의 k번째 call ↔ 그 뒤 k번째 tool 메시지"로 대응시킵니다. 수정 범위는 작지만 메시지 순서에 대한 암묵적 가정에 의존합니다.
3. **OpenAI 경로에서는 서버가 준 ID를 메시지 dict에 숨겨 두었다가 재사용하기** — 1번과 2번의 중간입니다.

**관련 학습 개념**: *API 계약(프로토콜 불변식)과 어댑터 패턴* — 여러 백엔드를 하나의 인터페이스로 감쌀 때는, 가장 엄격한 백엔드의 불변식을 공통 계약에 담아야 합니다.

### 2-4. [중요] 영상 *이름*을 작업 식별자로 써서 재업로드·취소 후 재시작에서 상태가 섞입니다

**왜 문제인가** — 이름 하나에 여러 의미가 겹쳐 있어서 생기는 시나리오 두 가지입니다.

**(a) 같은 이름으로 다시 업로드할 때**
`upload_video`는 `uploads/{이름}`을 그대로 덮어쓰지만, `analysis/{이름}.json`과 `.lines.npz`는 남겨 둡니다. 그러면 `/videos`가 `analyzed: true`를 내려 주고, 화면은 **새 영상 위에 옛 영상의 박스·3D 트윈·통계**를 겹쳐 보여 줍니다. 그 이름의 분석이 진행 중일 때 다시 업로드하면, 분석 스레드가 읽고 있는 파일이 중간에 바뀝니다.

**(b) 대기 중에 취소하고 바로 다시 시작할 때** (다른 영상을 분석 중이라 큐에 대기하는 상황)
1. `POST /analysis/x?mode=realtime` → job A 생성, `_run_analysis(x, "realtime")`이 큐에 들어감
2. `DELETE /analysis/x` → job A의 `state = cancelled`
3. `POST /analysis/x?mode=precise` → `analysis_jobs[x]` = job B, 두 번째 작업이 큐에 들어감
4. 첫 작업이 실행되면 `job = analysis_jobs[name]`(`:275`)으로 **job B**를 가져옵니다. B에는 cancel이 없으므로 realtime 분석을 끝까지 돌리고 B를 `done`으로 표시합니다.
5. 그다음 두 번째 작업이 B를 다시 `running`으로 바꿉니다.

결과적으로 사용자는 취소한 분석이 실행되는 것을 보고, 진행률이 100% → 0%로 되돌아가며, `mode` 표시도 실제 모드와 다릅니다.

**생각해볼 질문**
- "영상"(내용), "업로드"(어느 시점의 파일), "분석 작업"(한 번의 실행)은 각각 다른 생명주기를 가집니다. 지금은 셋 다 파일 이름 하나로 식별되는데, 각각 어떤 식별자가 필요할까요?

- 같은 이름의 재업로드는 "덮어쓰기"로 해석해야 할까요, "새 영상"으로 해석해야 할까요? 어느 쪽이든 옛 분석 결과는 어떻게 처리되어야 할까요?

**선택 가능한 접근**

### 2-10. [사소] 클라이언트가 보낸 텍스트가 시스템 프롬프트와 assistant 이력으로 그대로 들어갑니다

**왜 문제인가**
- `match_overview`의 `video`(= 업로드 파일명)가 **시스템 프롬프트 안의 "경기 개요"**에 들어갑니다. 업로드 파일명은 사용자가 정하는 텍스트라서, 파일명에 지시문을 넣으면 시스템 수준 문맥에 섞입니다(간접 프롬프트 인젝션).

도구가 모두 읽기 전용이고 로컬 단일 사용자 앱이라 피해는 "그럴듯한 틀린 답" 정도로 제한됩니다. 그래서 심각도를 사소로 두었습니다. 다만 개념 자체는 배포를 생각할 때 꼭 알아 둘 만합니다.

**선택 가능한 접근**
1. 개요는 수치·열거형 필드만 넣고 자유 텍스트(파일명)는 빼거나 user 메시지 쪽으로 옮기기
2. 이력은 서버 세션에 저장하고 클라이언트는 세션 ID만 보내게 하기
3. 지금 구조를 유지하되 문서에 신뢰 경계를 명시하기
