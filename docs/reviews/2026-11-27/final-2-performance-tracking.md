# 섹터 2 리뷰 · 전체 영상 처리 성능과 선수 신원

## 1. 잘한 점

- 위험 구간을 합칠 때 원래 사건 번호를 보존한다. 겹치거나 바로 붙는 구간은 한 번 읽고, 같은 시작 프레임의 선수는 함께 전파하며, 시작점이 바뀌면 추적 상태를 초기화한다. 앞선 ID 교체가 다음 사건의 시작 박스를 바꾸면 해당 사건만 다시 계산한다. 실제 전체 영상에서는 11개 묶음 중 처리 과정에서 사건 2개를 재계산했다.
- 구간 병합과 판정 로직을 GPU 모델에서 분리했다. 가짜 추적기로 단건·묶음 수리 결과, 짧게 읽힌 클립, 실제로 엇갈려 달리는 선수의 ID 보존을 확인하는 테스트가 있다. OCR도 판독기를 주입해 투표·동시 등장 충돌·재연결을 검사할 수 있다. [tests/test_sam_video_batch.py:74] [tests/test_sam_video.py:108] [tests/test_identity.py:92]
- 정밀 모드의 기본 설정은 장치와 transformers 설치 여부를 보고 선택 기능을 켠다. GPU가 없는 기본 환경에서는 색 기반 팀 분류를 사용하고 SAM3·OCR 단계를 생략한다. SAM3 수리에는 일반 후처리도 필요하다는 조건을 프로필에 명시했다. [pipeline/main_pipeline.py:153]
- 교체 판단에 여러 프레임을 쓰고 교차 일치 횟수와 평균 IoU 차이를 남긴다. 10부 문서에는 기준을 낮췄을 때 실제 교체 한 건과 육안으로 구별하기 어려운 두 건이 함께 추가된 관찰이 있다. 9부 문서도 OCR의 미확정과 오독을 구분하고 직접 확인한 확정 트랙이 8개였음을 밝힌다.

## 2. 개선 제안

### 수리 실패 후 프레임과 신원 자료가 서로 다른 ID를 쓸 수 있다 · 중요

[tracking/sam_video.py:441] [pipeline/video_analysis.py:363]

끊김 연결은 즉시 원본 프레임에 적용하지만 크롭과 라벨은 수리 함수가 반환한 뒤 옮긴다. 연결을 마치고 겹침 사건의 특징을 계산하다 GPU 메모리가 부족해지면 예외 처리 후에도 프레임에는 새 ID가 남는다. 이어지는 OCR은 이미 사라진 자식 ID의 판독을 버릴 수 있다. 특히 설정의 120프레임은 구간을 **합칠 때** 검사한다. 단일 장기 겹침은 그 길이 그대로 들어가고 같은 시각에 시작하는 객체 수도 제한하지 않는다. 사건별 재시도 역시 현재 실패 경로에 없다. [tracking/sam_video.py:138] [tracking/sam_video.py:279]

- 생각해볼 질문 — 두 번째 수리 단계가 실패했을 때 첫 단계까지의 결과를 사용자에게 제공할 가치가 있을까?
- 선택지 — 수리할 ID 변경을 임시 상태에 모아 성공 시 함께 반영하면 복구가 단순하지만 작업 메모리가 늘어난다. 단계별로 변경 목록과 부가 자료를 함께 확정하면 일부 성과를 살릴 수 있지만 실패 지점을 구분해야 한다. 묶음 할당 실패 때 사건별 추적으로 재시도하면 캐시 부담이 줄지만 긴 사건의 처리 시간과 실패 정책은 별도로 정해야 한다.
- 배울 개념 — 원자적 상태 변경과 GPU 최대 할당량. 가짜 추적기가 연결 직후 예외를 내도록 하면 GPU 없이도 실패 후 ID 일관성을 확인할 수 있다.

### 교체한 선수의 팀 판정에는 교체 전 표본이 남는다 · 중요

[pipeline/video_analysis.py:313] [pipeline/video_analysis.py:373] [pipeline/video_analysis.py:396]

서로 다른 팀 선수가 초반에 겹쳐 ID가 뒤바뀌면 SAM3가 이후 박스를 올바르게 교환해도 팀 분류용 크롭·색·라벨 표는 이전 ID에 남는다. 프레임 번호로 소유자를 교환하는 곳은 등번호 크롭뿐이다. 긴 뒷구간 표본이 우세하면 올바르게 읽은 등번호가 반대 팀에 배정되고 같은 팀·같은 번호 재연결에도 영향을 준다.

- 생각해볼 질문 — 최종 선수 ID에 속하는 표본인지 팀 분류 직전에 어떻게 확인할까?
- 선택지 — 기존 JerseyCropBank.swap처럼 팀 표본에도 시각을 보존해 매핑을 재생하면 영상 재읽기를 피할 수 있지만 라벨 집계 구조가 달라진다. 교체된 두 트랙만 최종 박스에서 다시 표집하면 기존 분류기를 유지할 수 있지만 디코딩 비용이 든다.
- 배울 개념 — 시간 구간별 ID 매핑과 파생 자료의 일관성.

### 혼잡한 장면에서 단일 프레임 또는 동률 투표가 영구 연결을 결정한다 · 중요

[tracking/sam_video.py:429] [tracking/identity.py:184] [tracking/identity.py:233]

가려진 선수가 다시 나타날 때 두 후보가 모두 IoU 0.5를 넘으면 첫 박스에서 조금 더 겹친 후보가 선택된다. 동점이면 나중에 순회한 후보가 이긴다. OCR에서도 같은 팀의 18번과 16번 판독이 각각 두 번씩 같은 높은 신뢰도로 나왔다면 1위 점유율이 정확히 50%여도 통과하고 먼저 입력된 번호가 이긴다. 그 번호의 다른 트랙과 관측 프레임이 겹치지 않으면 이동 거리 확인 없이 병합된다. 9부의 표본 검토는 이런 경계 사례의 오연결률까지 측정하지 않았다.

- 생각해볼 질문 — 1위 점수가 기준을 넘더라도 2위와 구별하기 어려운 후보는 보류하는 편이 좋을까?
- 선택지 — 1·2위 차이가 작은 사건을 보류하면 잘못된 병합을 줄이는 대신 실제 끊김이 더 남는다. SAM은 재등장 뒤 여러 프레임의 일치도로, OCR은 시간 차 대비 이동 가능 거리나 독립된 시점의 판독으로 교차 확인하면 근거가 늘지만 카메라 이동·장면 전환을 고려해야 한다.
- 배울 개념 — 임계값 보정과 기권 판정. 맞게 읽은 번호 비율과 실제로 같은 선수를 이은 비율을 따로 측정할 수 있다.

### 저장된 분석에 등번호를 추가할 때 경기장 좌표의 ID가 남는다 · 중요

[scripts/identify_jerseys.py:103] [scripts/identify_jerseys.py:110]

이미 보정된 결과에서 두 트랙을 합치면 identify는 frames를 바꾸고 스크립트는 teams에서 자식을 지운 뒤 저장한다. 기존 world, roles, track_labels에는 이전 ID가 남을 수 있다. 화면 박스는 한 선수인데 경기장 궤적은 두 선수로 갈라지는 입력이다. 일반 분석 경로는 신원 처리 뒤에 경기장 좌표를 만든다는 점이 다르다.

- 생각해볼 질문 — 저장 파일을 다시 열었을 때 박스와 좌표에서 같은 선수를 조회할 수 있어야 하는가?
- 선택지 — 동일한 매핑을 모든 ID 기반 자료에 적용하면 기존 좌표를 살리지만 병합 경계의 평활화는 다시 판단해야 한다. 파생 좌표·역할을 재생성하면 일반 경로와 일치하지만 처리 비용과 필요한 보정 정보가 늘어난다.
- 배울 개념 — 저장 스키마의 참조 무결성과 재계산 범위.

### 실행 순서와 모델 로딩을 시간 해석에 포함할 필요가 있다 · 권장

[scripts/eval_suite.py:255] [scripts/eval_suite.py:261] [docs/final-report/final-report.html:76]

검출기는 타이머 전에 초기화하지만 SAM3와 OCR은 분석 중 첫 호출에서 가중치를 읽는다. 따라서 보고서의 ‘모델 초기화 제외’는 검출기 초기화로 범위를 좁혀야 한다. 변형별 명시적 워밍업이나 반복 없이 같은 프로세스에서 순서대로 실행한다. 팀 분류만 11.3초 차이가 나므로 전체 절감 32.7초를 모두 SAM 묶기의 효과로 돌릴 수 없다.

- 생각해볼 질문 — 처음 영상을 여는 사용자의 대기 시간과 준비된 모델의 처리량 중 어느 쪽을 설명하려는가?
- 선택지 — 현재 한 쌍을 유지하고 포함된 로딩과 실행 순서를 표기하면 비용 없이 관측값을 정확히 설명할 수 있다. 같은 영상을 순서를 바꿔 여러 번 측정하고 최초 실행과 이후 실행의 중앙값·범위를 나누면 변동성을 추정할 수 있지만 GPU 시간이 더 든다.
- 배울 개념 — 짝지은 벤치마크, 순서 효과, 측정 구간의 경계.

### CSV 경로가 실제 영상 FPS를 사용하지 않는다 · 권장 · 기준 브랜치에도 존재

[pipeline/main_pipeline.py:313] [pipeline/main_pipeline.py:338] [pipeline/main_pipeline.py:460]

process_video는 FPS를 읽지만 process_frame은 처리 횟수를 먼저 올린 뒤 30으로 나눈다. 25fps 영상에서 원본 인덱스 249의 시각은 9.96초이고 CSV에는 약 8.33초가 들어간다. 반면 보고서의 analyze_video는 원본 프레임마다 배열 자리를 확보하고 건너뛴 탐지 사이를 보간한다. 이 CSV 문제가 B의 1,054프레임 측정에 전파된 근거는 없다.

- 생각해볼 질문 — FrameData가 처리 호출 횟수와 원본 영상 시각 중 무엇을 표현해야 할까?
- 선택지 — 고정 FPS 입력은 원본 인덱스와 FPS를 전달하면 계산이 단순하다. 디코더 시각을 전달하면 가변 FPS도 표현할 수 있지만 시각이 누락된 입력의 처리 기준이 필요하다.
- 배울 개념 — 프레임 인덱스, 샘플링 간격, 영상 시간축.

## 3. 보고서 주장과 코드의 일치 여부

| 주장 | 대조 결과 |
|---|---|
| 전체 4.4%, SAM3 11.1% 단축 | sam_batch.json과 .md 모두 동일 영상 1,054프레임, 30fps, 정밀 프로필과 같은 보정 설정이다. 변형 간 설정 차이는 batch뿐이다. 전체 741.8→709.1초, SAM3 222.3→197.7초로 비율이 맞는다. 한 쌍의 실측이라는 보고서 표현도 적절하다. |
| GPU 최대 할당량 증가 | 5.02→6.72 GiB로 1.70 GiB 증가했다. eval_suite가 수집하는 값은 PyTorch 최대 할당량이므로 표 제목과 맞는다. 이 값은 다른 입력에 적용할 안전 상한을 제공하지 않는다. |
| 두 실행의 결과 일치 | tracking-comparison.json은 박스와 경기장 좌표가 달라진 프레임 각 0개, 호모그래피와 SAM 판정 일치를 기록한다. 두 행 모두 연결 2건, 교체 3건이고 쌍과 시각도 같다. 같은 결과를 낸다는 검증 범위는 이 영상과 가짜 추적기 테스트 사례까지다. |
| 품질 지표 | 트랙 49개, 화면 안 끊김 후보 1건, 공 기록 1,054프레임, 등번호 확정 18개가 두 행에서 일치한다. compare_tracking의 끊김은 후보 탐색 규칙의 출력이고 공 기록은 후처리된 결과이므로 실제 신원 오류나 원시 검출 재현율은 별도 정답 자료가 있어야 측정할 수 있다. |
| 측정 시간의 경계 | 지표 집계는 전체 타이머 밖이다. 지연 로딩되는 모델 초기화는 타이머 안이므로 보고서 문구에 보완이 필요하다. |

## 4. 다음에 공부해보면 좋을 주제

- 같은 번호의 경쟁 후보, 동시 재등장, 서로 다른 팀의 교차를 따로 표집해 연결 정밀도·재현율을 비교하는 방법.
- 사건 길이와 동시 객체 수를 각각 늘려 최대 할당량을 측정하고 프레임 특징 캐시의 이득과 비교하는 방법.

검증 범위는 지정 소스와 테스트의 정적 검토, 저장된 성능·동일성 증거 대조다. 허용된 pytest 명령은 환경에서 python.exe를 열 수 없어 테스트 수집 전에 중단됐다. GPU 실행을 새로 측정하지 않았다.
