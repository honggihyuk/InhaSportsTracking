## 1. 잘한 점

- 새 지표를 기존 저장 형식에 추가해 API 사용법을 유지했다. 등번호가 확정된 선수에게만 값을 넣고 패스 네트워크를 통계에 추가한다. 서버는 저장된 통계 객체를 그대로 반환하며, 결과가 없을 때와 보정 전일 때는 각각 이유를 담은 404를 준다. 프런트의 공통 JSON 요청 함수와 경로가 맞고, 화면은 시간 범위에 따라 네트워크를 계산할 수 있다. [analysis/stats.py:273], [backend/server.py:484], [frontend/src/components/api.js:144], [frontend/src/components/AnalysisViews.jsx:274]
- 등번호와 추적 ID를 구분해 질의 도구에 설명했고, 등번호가 없으면 이미지 확인을 안내한다. 기존 저장본에서 등번호 키가 빠져도 순위 조회는 동작한다. GPU 분석에서는 새 OCR·영상 추적기도 기존 정리 루프에 포함해 분석 중 예외가 나도 모델을 내려놓는다. [agent/tools.py:33], [agent/tools.py:128], [backend/server.py:301]
- 제출 자료의 경계가 분명하다. 학습 가중치와 업로드 영상, 로컬 환경 파일을 무시하고 키 입력 예시는 자리표시자를 쓴다. 약 1 MB PDF와 화면 캡처는 README나 보고서에서 바로 확인할 수 있는 제출물이다. 이번 변경에서 이 바이너리를 제외해야 할 구체적 문제는 발견하지 못했다. [.gitignore:14], [.gitignore:57], [docs/guides/ROBOFLOW.md:21], [README.md:7]

## 2. 개선 제안

### ① 같은 이름으로 업로드할 때 영상과 통계의 소유 관계 보존

**[backend/server.py:168] · 중요** (기존 경로). 두 번째 경기 영상을 첫 경기와 같은 이름으로 올리면 원본을 먼저 덮어쓰고 나서 유효성을 검사한다. 성공하면 이름으로 연결된 기존 분석 JSON과 라인 파일이 남아 새 영상에 이전 경기의 트윈·통계·VLM 답이 붙을 수 있다. 손상된 파일이면 183행에서 해당 경로를 삭제하므로 원래 재생되던 영상도 사라진다.

- **생각해볼 질문** 사용자가 올린 파일명은 표시 이름인가, 분석 결과가 영구히 참조할 영상의 식별자인가?
- **선택지** 중복 이름을 409로 거절하면 변경량이 작지만 재업로드에 새 이름이 필요하다. 업로드별 ID를 발급하면 같은 이름의 두 경기를 보존할 수 있지만 기존 URL과 샘플에 대한 호환책이 필요하다. 교체가 의도한 기능이라면 임시 파일 검증 후 영상과 결과 버전을 함께 전환하는 방법도 있다.
- **학습 개념** 리소스 식별, 원자적 교체, 파생 데이터 무효화.

### ② 대기열에서 취소한 작업과 새 분석의 상태 분리

**[backend/server.py:275] · 중요** (기존 경로). 다른 영상이 단일 워커를 사용하는 동안 A를 대기시켰다가 취소하면 416~417행에서 즉시 재시작이 가능해진다. 새 요청은 403행에서 이름 A의 상태 객체를 교체한다. 먼저 제출된 콜백도 실행 시점에 이름 A로 조회하므로 새 객체를 잡고 예전 모드로 분석·저장하거나 새 요청을 먼저 완료 처리할 수 있다. 실행 중 취소는 상태가 달라 이 순서와 구별해야 한다. 자동 보정 워커도 같은 조회 패턴을 쓴다.

- **생각해볼 질문** 큐에 넣은 시점의 작업과 저장 시점의 작업이 같음을 무엇으로 확인할까?
- **선택지** 작업 객체를 콜백에 직접 전달하고 저장 전에 현재 작업인지 확인하면 재시작을 허용할 수 있다. 취소한 작업이 큐에서 제거되거나 종료될 때까지 기존 409 규칙을 유지하면 상태 관리는 단순하지만 대기 시간이 생긴다.
- **학습 개념** 작업 수명 주기, 취소의 의미, 경쟁 상태.

### ③ OpenAI 호환 모드에서 도구 호출과 응답 연결

**[agent/llm.py:127] · 중요** (기존 경로). 제공자가 준 호출 ID는 146행에서 사라지고, 대화를 다시 보낼 때 호출에는 메시지 위치와 호출 순번을 붙인다. 러너가 70행에서 만든 도구 결과에는 ID가 없어 어댑터가 결과 메시지 위치만으로 다른 값을 만든다. 호출 하나부터 짝이 맞지 않으므로 이를 검사하는 서버는 첫 조회 이후의 답변 요청을 거절할 수 있다. 같은 도구로 두 팀을 조회할 때는 이름만으로 구별할 수도 없다.

- **생각해볼 질문** 로컬 모델과 호환 서버가 같은 러너를 쓸 때 호출의 정체성은 어느 계층이 책임질까?
- **선택지** 내부 호출에 선택적 ID를 담아 결과까지 전달하면 제공자 기록과 추적이 쉽다. 어댑터가 한 턴의 호출·결과 쌍에 같은 합성 ID를 배정하면 러너 변경은 작지만 누락된 결과와 순서 검사가 필요하다.
- **학습 개념** 메시지 상관 ID, 다중 도구 호출의 대화 계약.

### ④ 등번호 중복과 출력 한도를 도구 수준에서 다루기

**[agent/tools.py:132] · 권장**. 같은 팀의 끊어진 두 트랙에 같은 등번호가 남으면 팀을 지정한 뒤에도 동일 후보가 둘이다. 현재 안내는 다시 팀을 지정하라고 하므로 사용자가 같은 질문을 반복할 수 있다. 후보 전체와 큰 `top`에 대한 순위 전체가 반환되고, 러너의 6,000자 제한은 모델 메시지에만 적용된다. HTTP 응답의 단계 기록에는 이미지 이외의 결과가 그대로 남는다. [agent/tools.py:153], [agent/runner.py:29], [agent/runner.py:68]

- **생각해볼 질문** 팀까지 받은 후에도 후보가 여러 명이면 사용자가 무엇을 보고 고를 수 있을까?
- **선택지** 팀 중복과 팀 내부 중복을 구분하고 후보 ID·관측 시점을 제한된 수만 제시하면 한 번 더 물어 정확히 고를 수 있다. 처음부터 후보 목록과 잘림 여부를 공통 형식으로 반환하고 순위·후보 상한을 스키마와 실행부 양쪽에 두면 긴 경기에서도 응답 비용이 예측 가능하지만 도구 설명을 변경해야 한다.
- **학습 개념** 모호성 해소, 입력 검증, 출력 예산.

### ⑤ 실험에 쓰인 모델을 새 PC에서 식별할 수 있게 하기

**[configs/model_config.yaml:21] · 권장**. 기본 설정은 상대 경로와 자동 장치 선택을 사용한다. 8부의 D 드라이브는 학습 PC의 예시다. 실제 재현 차이는 가중치가 없을 때 생긴다. 새 클론에서는 경고 후 COCO 가중치로 계속 실행할 수 있어 정밀 모드가 완료돼도 보고서 1절과 같은 탐지기를 사용했다는 보장이 없다. 모델 가이드의 GPU용 YOLO11s 권장은 탐지 백엔드를 자동 선택하는 README와 적용 조건을 구분하기 어렵다. [tracking/rfdetr_detector.py:70], [docs/guides/MODELS.md:74], [README.md:141]

- **생각해볼 질문** 실험 결과만 받은 동료가 실제로 선택된 모델·장치와 체크포인트를 구별할 수 있을까?
- **선택지** 측정 JSON에 실제 백엔드·장치·가중치 해시와 대체 여부를 기록하면 일상 사용의 자동 대체를 유지한다. 보고서 재현용 프로필에서만 해시가 맞아야 시작하게 하면 잘못된 비교를 일찍 막지만 가중치를 준비해야 한다. 어느 쪽이든 YOLO 가이드에 해당 백엔드의 적용 조건을 명시할 수 있다.
- **학습 개념** 선언한 설정과 실제 실행 설정, 실험 산출물의 출처.

### ⑥ 최종 제출 코드와 D 브랜치 결과 구별

**[docs/final-report/final-report.html:100] · 중요**. 6절은 등번호 교정·근거 없는 수치 표시를 구현했다고 쓰고 마지막에 D의 별도 커밋과 14부를 인용한다. 제출본 러너는 도구 결과를 메시지에 넣고 모델의 문장을 반환하며, 해당 경로에 답변 수치를 사후 대조하는 단계가 없다. 제출 트리에서 14부 파일도 찾지 못했다. 독자는 D 기능까지 설치되고 측정만 남았다고 이해할 수 있다. 보고서가 구분한 ABC 149개와 D 브랜치의 150개도 서로 다른 검증 기록이다. [agent/runner.py:62], [agent/runner.py:82]

- **생각해볼 질문** 제출본만 실행한 평가자가 D 항목에서 직접 확인할 수 있는 동작은 어디까지인가?

- **학습 개념** 릴리스 범위, 구현 증거와 실측 증거.

### ⑦ 근거 파일에서 생성 절차까지 역추적하기

**[docs/final-report/final-report.html:109] · 권장**. 성능·속력 표에는 생성 도구가 있지만 6절의 옵션만으로는 후속 비교 입력을 보존하지 않는다. 평가 도구는 결과 표 저장에 `--out`, 변형별 분석 저장에 `--save-dir`를 받으며, 속력 비교는 입력 분석 JSON과 `--json`이 필요하다. 또한 이름이 비슷한 `compare_tracking.py`는 트랙 집계치를 출력한다. 근거의 프레임별 변경 수와 호모그래피 동일 여부를 산출하는 절차는 거기서 확인할 수 없다. [scripts/eval_suite.py:325], [scripts/diagnose_speed.py:321], [docs/final-report/evidence/tracking-comparison.json:3]

- **학습 개념** 실험 계보, 재실행 가능한 비교.

## 4. 다음에 공부해보면 좋을 주제

- 대기·취소·재시작을 상태 전이표로 그린 뒤, 오래된 작업이 새 결과에 쓸 수 있는 시점을 찾아보는 동시성 테스트 설계.
- 모델 없이도 단일 호출과 다중 호출의 직렬화 결과를 검증하는 프로토콜 계약 테스트.
- 한 개의 보고서 수치에서 입력 영상·모델·설정·생성 명령까지 거슬러 올라가는 재현성 기록 설계.
